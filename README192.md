# 2G 的视频在网页版传了两次都失败：先算清 2GB 上限、1900M 分卷和网盘链接这三条路，再动手

上周三晚上十一点，同事在群里催一段活动录像，手机拍的 4K，2G 出头。我网页版正开着，想着把文件拖进对话框就完事。第一次传到 68% 就不动了，红色小字提示「上传失败，点击重试」；第二次学乖了，刷新页面重新拖，进度条走到一半又从头来过。折腾到快十二点，我才停下来去查一个最基础的问题——网页版到底能传多大。

答案很短：2GB。而我那个文件是 2.3GB。后面那次成功，靠的不是网速好，是先算清了字节数，再用 7-Zip 切成两卷发出去。

这篇写的就是撞墙之后摸出来的三条路：把文件做小、切成卷、换成一个链接发出去。哪里会卡、菜单在哪、报错长什么样，我都按当时的顺序记下来了；网页版跟文件相关的其余设置，可以在 [这个中文指南站](https://tlgrwo-web.com) 上按浏览器分开看。

## 一、上限是 2,147,483,648 字节，"2G"是个四舍五入的幻觉

先把这个数字钉死。手机相册里写"2.0 GB"的视频，实际可能是 2.1GB 也可能是 2.3GB，因为它按 1000 进位显示；而网页版的判断按字节来，卡的就是 2,147,483,648 这个数。在 Windows 上右键文件看属性，别只看"大小"，要看后面括号里的字节数——"大小"和"占用空间"经常差出一截，尤其视频这种大文件。

| 发送方情况 | 单文件上限 | 实际会先撞上的地方 |
| --- | --- | --- |
| 普通账号，网页版直接拖进去 | 2GB（2,147,483,648 字节） | 私聊、群组、频道都一样，看的是发送方等级 |
| 开了 Premium 的账号 | 4GB | 接收方不用开也能正常收 |
| 借第三方机器人转发或搬运 | 上传 50MB、下载 20MB | 这是 Bot API 的限制，跟你用哪个浏览器没关系 |
| 一次拖入多个文件 | 单个仍受上面限制 | 总量过大时浏览器标签页会先崩，比超限更麻烦 |

还有一层很多人忽略：上限由账号决定，但**能不能传完由浏览器决定**。同样是 1.8GB 的文件，有人一次过，有人传三遍，差别全在标签页有没有被系统挂起、上传中途有没有切网络。

## 二、三种失败现场，报错不一样，处理方式也不一样

传大文件失败，声音都差不多，成因差别很大。我按遇到过的顺序排一下，看提示就能对号：

1. **刚点发送就红字**，提示「文件过大，无法发送」或 File is too large——真超限了。这种别重试，重试一百次也是同一个结果，去算字节数、准备分卷。
2. **传到一半停住**，提示「上传失败，点击重试」，有的浏览器开发者工具里能看到 `FILE_PART_x_MISSING` 这类字样——分片丢了。原因通常是标签页在后台被冻结、Wi-Fi 掉了一下、或者你中途切了代理节点。这种情况刷新重传往往还是失败，得先把浏览器和网络按住。
3. **传成功了，对方点开黑屏或提示无法播放**——文件完整，但编码不对。iPhone 默认拍的 H.265（HEVC）视频，网页端和一部分安卓机解不了码。这种最冤，白传一遍，得先转成 H.264。

前两种是"传不上去"，第三种是"传上去了没用"。判断清楚再动手，能省掉一整晚。

## 三、路径一：把文件做小，八成的情况到这一步就结束了

如果对方只是要"看这段录像"，根本不需要原始文件。我那次是压到 280MB 直接发出去的，画质在手机上看不出差别。

命令行一条就够（装了 ffmpeg 的话）：

```bash
ffmpeg -i input.mp4 -c:v libx264 -crf 26 -preset veryfast -vf scale=-2:720 -c:a aac -b:a 128k output.mp4
```

`-crf 26` 是画质档位，数字越大压得越狠，26 到 28 之间对录像类素材基本够用；`scale=-2:720` 把高度压到 720p，宽度按比例自动算。2.3GB 的 4K 素材，跑十来分钟能出 300MB 上下。

只要其中一段的话，别整段压，直接切：

```bash
ffmpeg -ss 00:12:30 -t 90 -i input.mp4 -c copy clip.mp4
```

从 12 分 30 秒开始，取 90 秒，`-c copy` 不重新编码，几秒钟就出来，画质一点不掉。不爱敲命令就用 HandBrake，预设选 Fast 720p30，质量那栏填 RF 26，图形界面比命令行稳。

## 四、路径二：分卷，唯一能"原样送达"的办法

必须给原始文件的时候，只有切卷这一条路。注意一个前提：**分卷不是绕过限制，是让每一卷都落在限制以内**。

1. 先算卷数。右键文件看字节数，除以 1900MB 向上取整。2.3GB 是 2 卷，5GB 是 3 卷。留 100MB 余量是因为压缩包本身有头部开销，卡着 2000MB 切经常有某一卷超出去。
2. 装 7-Zip，右键文件 →「添加到压缩包」。压缩格式选 `7z`，压缩等级选「仅存储」——视频再压也小不了多少，白白耗掉半小时。
3. 分卷大小那一栏填 `1900m`，注意是小写 m，填 `1900M` 有的版本会当成 1900 字节。
4. 生成的卷会叫 `活动录像.7z.001`、`.002`。名字别改，序号就是拼接顺序。
5. 全部卷一次发完，别今天发一卷明天发一卷。中间漏一卷，对方下载完也解不开，还得回来问你。
6. 发完补一句"共 2 卷，缺一卷解不开"。这句话能省掉对方半小时的自我怀疑。

接收方那边，把全部卷下到同一个文件夹，右键 `.001` → 7-Zip →「提取到当前文件夹」，它会自己把后面的卷串起来。用 WinRAR 的话，切分卷那一栏填 1900m，格式建议选 RAR4，老版本 WinRAR 也能打开。

macOS 和 Linux 不用装软件：`split -b 1900m video.mp4 video.part-`，接收方 `cat video.part-* > video.mp4` 就还原了。缺点是对方得会这条命令，发给不熟的人还是 7z 省事。

## 五、路径三：网盘与云端直链，把"发送"变成"给个地址"

同一个文件要给五个人，一条条发是折磨自己。这时候把文件挪到别处，聊天里只发链接，反而干净。

| 替代方式 | 对方要做什么 | 谁在上传 | 适合什么场面 |
| --- | --- | --- | --- |
| 网页版直传 | 点开就看 | 你，一次 | 一对一，几十秒能传完的小文件 |
| 1900M 分卷 | 下全所有卷、装解压工具 | 你，一次 | 必须原样交付原始素材 |
| 网盘分享链接 | 可能要登录、可能被限速 | 你，一次 | 群里多人要同一份 |
| 对象存储签名直链 | 点开即下 | 你，一次 | 团队交付、有明确有效期要求 |

发链接有两个小动作值得做。一是**单独发一条消息**，等 Telegram 把预览卡片抓出来，再补一句"有效期 7 天"；链接混在一大段文字里，手机端很容易点错。二是**别用短链服务**，多一跳跳转就有掉预览、掉权限的风险。

还有一种不算替代、但很好用的中转：把文件发到自己的「收藏夹（Saved Messages）」，换台设备再下载。它不解决上限问题，解决的是"这台机器传不上去、那台机器网络更好"的现实。

## 六、上传那几个小时，别让浏览器和系统捣乱

1.8GB 的文件，按 10Mbps 上行算要传二十多分钟，慢一点的宽带上限能到两小时。这段时间里，最先出问题的往往不是网络，是浏览器的省电策略。

Chrome 从 117 版开始默认开了「内存节省程序」。地址栏输入 `chrome://settings/performance`，把「内存节省程序」关掉，或者在下面的白名单里加上你用的站点——否则标签页切到后台十几分钟就被挂起，进度条停在那里，你回来一看还以为是网断了。

Edge 对应的是 `edge://settings/system`，「系统和性能」里把「使用睡眠标签页节省资源」关掉，或者对这个站点设例外。Safari 要留意「标签页组」自动休眠，长时间上传时把这个标签页单独拉出来，别塞在组里。

系统这一层还有两个坑：Windows 的「电源与睡眠」把屏幕和睡眠都设成"从不"，笔记本合盖前先确认不会休眠；上传期间别去清缓存，也别用无痕窗口——无痕窗口一关，传到 90% 的东西一起消失。

网络这边，有线优先；上传时不要切代理节点，连接一断就得从头再来；同一时间别开着另一个大文件下载，上行被抢走，两边都慢。

## 七、下次动手前的 30 秒

现在我的顺序固定成这样，基本不会再传第二遍：

1. 右键看字节数，超过 2,147,483,648 就认命走分卷。
2. 对方只是要看内容 → 压到 720p 或截片段，一条 ffmpeg 解决。
3. 必须原样给 → 7-Zip 按 1900m 切卷，一次发全。
4. 要发给一群人 → 传网盘，聊天里发一条带有效期的链接。
5. 都在自己的设备之间 → 走收藏夹，别占着聊天窗口传。

那段 2G 的录像，压缩加切片之后是 280MB，发给同事用了四分钟。剩下那两卷原始素材是第二天早上传的，睡前把 Chrome 的内存节省程序关了，机器通宵没休眠，醒来正好传完。这类事的成本从来不在技术，在于你动手前有没有花那三十秒看一眼数字。

网页版本身的文件收、发、下载位置这些细节，[站上有按场景整理的步骤](https://tlgrwo-web.com)，配合上面的流程一起看，剩下的就是熟练度问题了。
