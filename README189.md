# 同一个词翻出三种写法之后：企业术语库怎么建、翻译 API 怎么挂、几千条批量任务怎么过一致性校验

一份 68 页的英文产品手册翻完，审校在第五章停住了。

同一个 `dashboard`，第三章叫"仪表盘"，第五章叫"控制面板"，附录里又成了"看板"。三个译者都没错，各自守着自己那套说法，从头到尾没人给过一份"只能这么写"的清单。返回按钮上的 `Back` 也一样，有的地方是"返回"，有的干脆留着英文。不是语言能力问题，是三个人在三个时间点各做了一次合理选择，而没有东西把它们绑在一起。

后来我把这个项目的术语收了口，顺手跑了一遍整套流程：建库、挂接口、跑批量、上校验。

## 一、术语失控不是译者的锅，是资产没落地

那本手册有三个来源：第三章是老译者手工翻的，第五章是外包团队机翻打底再改的，附录沿用旧版本。三条生产线，三套词汇，没有共用的"正确译法"来源。

术语最常见的死法是：词表存在某个人的 Excel 里，项目结束那一刻它就停止更新。下个项目启动，新译者拿不到，或者拿到三年前的版本，里面还写着已下线的产品名。每次翻译都在重新发明轮子，每次的轮子都不一样。

要解决的是**让正确译法成为一条能被程序读取、被接口调用、被脚本核对的数据**。做不到这点，再认真的审校也只是给上游擦屁股。

## 二、术语体系：把"唯一正确译法"变成可执行的数据

术语库不是一张词表，是分了层的规则集：

- **强制层**：产品名、功能名、UI 按钮、法律合规章节的固定表述。出现就必须这么写，改一个字母都算错。
- **建议层**：行业通用词。允许随上下文微调，不许换成另一个概念。
- **禁译层**：品牌名、缩写、代码标识符。列进这层比在文档里写十遍"不要翻译"有效。

最小可用的条目长这样，字段一个都别省：

| 字段 | 样例 | 为什么必须有 |
| --- | --- | --- |
| 源词（src） | `dashboard` | 匹配用的原始串，大小写敏感度单独声明 |
| 目标译法（tgt） | `仪表盘` | 唯一写法，多个时用 `\|` 分隔并标优先级 |
| 词性（pos） | `noun` | 避免 `export` 作动词和名词时打架 |
| 大小写（case_sensitive） | `true` | `EXPORT` 在按钮上、`Export` 在正文里，规则不同 |
| 级别（level） | `强制 / 建议 / 禁译` | 决定校验时是报错还是告警 |
| 适用产品线 | `PAM / SIEM` | 同一个词在不同产品里译法可能相反 |
| 生效版本 | `v3.2` | 术语会随产品改名失效，靠版本号管住 |

建库我这么走：

1. 从历史译文抽高频名词短语，按出现次数取前 300 到 500 个。别一上来做几千条的大库，做不完也没人维护。
2. 每个词定唯一译法，把"允许的变体"写进备注。像 `login` 到底允不允许写成"登陆"，当场拍死，别留给译者发挥。
3. 按上面字段整理成 CSV，**UTF-8 无 BOM**，表头英文小写。带 BOM 的表格导进去，第一列表头变成 `\ufeffsrc`，系统认不出来，整批条目全部跳过。
4. 进「术语库管理 → 新建术语库 → 导入条目」，导入后先看跳过行数。常见原因是 `tgt` 为空，或 `src` 含逗号没加引号。
5. 建完用五条典型句子试翻，确认强制层真生效，再往下接接口。

## 三、API 接入：术语库不随请求走，等于没建

最容易犯的错是库建好了，调接口时忘了带 ID。服务默认走通用模型，术语库在后台躺着，而你以为它生效了。

文本翻译的请求里，术语库 ID 作为参数跟着走，`signType` 要显式写 `v3`：

```
curl -s https://openapi.youdao.com/api \
  -d "q=Open the dashboard and check the alert list" \
  -d "from=en" -d "to=zh-CHS" \
  -d "appKey=YOUR_APP_KEY" -d "salt=1690000000" -d "curtime=1690000000" \
  -d "signType=v3" -d "sign=SHA256_SIGN" -d "vocabId=12345678"
```

签名有个坑我卡了半小时：v3 的 `input` 不是把 `q` 直接丢进哈希。**`q` 不超过 20 字用原文，超过 20 字取前 10 个字符 + 长度 + 后 10 个字符**，再和 `appKey + salt + curtime` 拼起来做 SHA256。少这一步返回 `{"errorCode":"202"}`，签名检验失败——先怀疑截断规则和编码，别怀疑 appKey 抄错。另一个是 `{"errorCode":"411"}`，访问频率受限，批量任务上不去多半是它。

还有一点：**不同接口的术语生效范围不一样**。文本接口带 ID 就生效；文档翻译把 ID 挂在任务参数上；图片翻译走 OCR 之后同一条链路，术语生效，但识别错字在先就对不上。站上 [企业翻译与术语、API 的接入说明](https://7169t.com) 把范围列在一起，接之前对一眼。

## 四、批量任务：几千条文案怎么跑才不自己打自己

那次是 3200 多条产品文案，一条条手工提交不现实。批量跑，稳定性比速度值钱。

1. **先去重**。3000 条里重复和近重复能占两三成，按原文哈希，同一句只请求一次，避免同一句话在不同批次翻出两种结果。
2. **按语义切分**。别按固定字数硬切，句子中间断开，术语匹配和上下文都出错。按段落或条目切，单条 500 字以内。
3. **分批加限速**。每批 40 条，并发压到 3 到 5，上限看控制台「调用统计」里当天的 QPS 曲线。撞上 411 就退避，别硬顶。
4. **失败落盘**。每批结果写文件，成功记 `行号 + 原文哈希 + 译文`，失败单独写 `failed.jsonl` 并带错误码。中途断电也不至于从头再来。
5. **指数退避重试**。超时和 411 可以重试；`102`（不支持的语言类型）和参数类错误重试一万次也不会成功，直接进人工队列。
6. **回填对行号，不对顺序**。并发跑完顺序一定是乱的，用行号或哈希回填，靠"第几条结果"必然错位。

产物是一张表：原文、译文、命中条目、是否强制层，这就是校验的输入。

## 五、一致性校验：三道闸，自动在前，人工在后

术语库解决"该这么写"，校验解决"真这么写了吗"。三道闸，越往前越便宜。

**第一道，术语命中率。** 拿库去撞译文，命中强制层的条目必须逐字一致。隐蔽情况是：源文里 `dashboard` 在，译文却是"面板"，不是故意违规，而是这条术语的生效版本没覆盖当前产品线。报出来先查 `适用产品线`，别急着改译文。

**第二道，结构性校验。** 这层跟术语无关，漏了代价最大：

- **占位符**：`{0}`、`%s`、`{{name}}` 的数量和顺序必须和原文一致。少一个，程序直接崩。
- **数字与单位**：`3.5 GB`、`12%`、日期格式。术语对、数字错，是最典型的"看起来没问题"。
- **大小写与标点**：UI 按钮首字母大写规则，中文全角标点。
- **禁译层词**：产品名和缩写必须原样保留。

**第三道，抽检。** 强制层条目全查，建议层抽三成，其余按段落抽一成。抽检是给前两道闸找漏。

报错看久了会形成条件反射，这张表是攒下来的：

| 症状 | 大概率原因 | 处理 |
| --- | --- | --- |
| 同一术语出现两种译法 | 该条目的 `适用产品线` 没覆盖当前文档 | 补产品线，或拆成两条独立条目 |
| 术语在库里却没生效 | 请求没带 `vocabId`，或带的是另一个库的 ID | 核参数与库 ID，抓一次原始请求看 |
| 术语对了，词性错了 | `pos` 缺失，动词被当成名词 | 补词性，同源词按词性建两条 |
| 批量结果行错位 | 按返回顺序回填，并发打乱了序 | 改用行号或原文哈希回填 |
| 文档翻译不一致，文本接口正常 | 文档任务参数漏了术语库 ID | 任务参数补 ID，重跑该文件 |
| 返回 `202` | v3 签名 input 截断规则没做 | 按「前 10 + 长度 + 后 10」重算 |

## 六、术语库也要版本号，也要回归集

术语会过期。产品改名、功能下线、说法变化，库不动，译文就"一致地错"下去，比不一致更难发现——校验全绿。

我给库打版本号，`v3.2-2026Q3` 这种，每次改动写清动了哪几条。再维护一份两百条的回归集，覆盖强制层条目和几个场景，改库前跑一遍，命中率掉了就是改坏了，回滚比重查快。

接口那边写死了库 ID，换库就等于换服务，ID 变更要走上线流程。库挂在团队账号下，别落在某个人手里。相关规则在 [术语统一与团队协作](https://7169t.com) 那部分也能对照。

## 一致性是流程长出来的，不是审校抠出来的

那份手册交付了，三个译者的译法收成一套，附录留英文的部分也有了规则。真正起作用的不是谁的语言水平，是三样东西：一份分层、带版本、能被程序读取的术语表；一次把库 ID 挂进请求的接口改造；一套自动跑在前面、人工压在后面的校验流程。

这三样建一次能用很久，新建产品线时只是加条目。想从零搭的，可以从 [有道翻译的使用与接入指南](https://7169t.com) 的企业部分看起，先弄明白几个接口怎么带术语，再决定批量任务按什么粒度切。先做小，跑通一条链路，比一上来铺几千条的大库靠谱得多。
