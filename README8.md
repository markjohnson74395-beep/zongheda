# 切回标签页才看见一屏未读？Chrome 后台冻结让 tg网页版消息延迟、掉线的 5 个开关与 3 步实测验证

昨晚十一点四十，我把网页版丢在一个后台标签里，切去写周报。等回来点开那个标签，群名后面挂着 27 条未读，右下角通知中心干干净净，一条都没响过。更别扭的是，消息时间戳全是十几分钟前的——它不是在后台悄悄收着，是在我切回来的那一秒才成批补上。

这种事撞多了就会误判成"网页版不稳"。同一个入口，前台开着就秒收，扔到后台就开始拖，问题不在线路，在 Chrome 怎么对待一个久未露面的标签页。下面按机制、开关路径、验证三步写清楚。

这篇只处理"后台延迟"这一个症状。其它登录、缓存、扩展类的问题，站上分了不同章节，可以对着 [Chrome 浏览器使用建议](https://tlgroc-web.com) 一节先建立整体印象。

## 一、机制：Chrome 不是"关掉"了你的标签，是给它降了三级

一个标签页从你切走那一刻起，会依次掉进三个更省资源的状态，很多人把它们混成一句"网页版在后台不刷新"。

- **隐藏但活着（hidden）**：页面还在跑，只是 Chrome 对隐藏超过 5 分钟的标签做定时器节流，`setInterval`、`setTimeout` 的最短间隔被压到大约 1 分钟一次。心跳包、重连倒计时、未读轮询全部变慢，你看到的是"慢半拍"，不是"没有"。
- **冻结（frozen）**：JavaScript 主线程被挂起，脚本一行都不执行。WebSocket 不再收发，页面自己也察觉不到已经断线。冻结期间对方发来的消息一条都不会落地，切回来才一次性涌入。
- **丢弃（discarded）**：内存紧张时整页被卸载。切回来是一次真正的重新加载，滚动位置回到顶部，没发出去的半句话也没了；如果会话票据恰好过期，就会演成"一回来就要求重新登录"。

| 生命周期状态 | 页面里实际发生的事 | 切回时的观感 | 后台期间的消息 |
| --- | --- | --- | --- |
| active（前台） | 一切正常 | —— | 实时到达，通知正常 |
| hidden（后台未冻结） | 定时器被节流到约 1 分钟一次 | 状态还在，就是慢半拍 | 延迟几十秒到一分钟 |
| frozen（冻结） | 脚本暂停，长连接停摆 | 冻结期界面静止，切回后成批补上 | 基本收不到，通知不弹 |
| discarded（丢弃） | 页面被卸载、内存回收 | 白屏一下、重新加载、草稿丢失 | 完全收不到 |

看清这张表就能解释那个最典型的困惑：**通知没响，往往不是权限没给，而是页面在你离开的第三分钟就已经冻住了**。通知要靠活着的页面去调用系统接口，页面停了，谁都替它发不出来。

## 二、设置路径：五个开关，从最省事到最彻底

这五条按"改动成本"排，前两条不碰任何设置，做完就能挡掉大半场景。

1. **把标签页固定住**。在标签上右键 → 固定。固定后的标签宽度收成一个图标，不会被随手关掉，也不容易被内存回收逻辑优先选中。要注意它只降低被丢弃的概率，**并不阻止冻结**。
2. **给它单独一个窗口**。`Ctrl + N` 开新窗口，或把标签直接拖出成窗。聊天一个窗口、文档一个窗口，比三十个标签挤在一起时被判定为"可回收"要稳得多。
3. **进内存节省程序的白名单**。地址栏输入 `chrome://settings/performance`，找到「内存节省程序」，下面有一栏「始终保持这些网站处于活动状态」，点「添加」，把网页版的域名填进去。这里有个版本差异：Chrome 108 刚上线时只有一个总开关，之后的版本把它拆成了几档强度，档位越高回收越积极——设置页里出现「适中 / 平衡 / 最大化」这类选项时，选最温和的一档，或者保持开启但把站点加进白名单。
4. **顺手看一眼节能模式**。同一个设置页往下，「节能模式」如果选了"始终开启"，笔记本一旦拔掉电源，页面刷新频率和后台活动会被进一步压制。改成「仅在设备使用电池时开启」，插电办公时就不会被这一层拖慢。
5. **实验室开关作为兜底**。输入 `chrome://flags`，搜索 `tab discarding`，把自动丢弃标签相关的项设为 `Disabled`，点右下角重启。这条只当兜底——Chrome 每次大版本升级都可能把它重置回默认。

还有一层常被漏掉：通知本身。`chrome://settings/content/notifications` 里确认网页版那条是「允许」而不是「询问」，因为「询问」状态下你不在页面上时，Chrome 会静默把弹窗丢掉，界面上什么提示都没有。系统层再确认一次——Windows 的「设置 → 系统 → 通知」里，Google Chrome 的通知开关要是开着的，「专注助手」或勿扰时段也会把弹窗吞掉。这两级的逐项对照在 [桌面通知开启与关闭](https://tlgroc-web.com) 那一节写得比我这里细。

## 三、验证方法：三步，把"感觉快了"变成能看见的数字

改完设置不验证，等于没改。三步按顺序做，十分钟内能出结论。

**第一步，看 Chrome 自己怎么标注这个标签。** 新开标签输入 `chrome://discards`。表格里每个标签都有一列 `Lifecycle state`，取值是 `ACTIVE`、`HIDDEN`、`FROZEN`、`DISCARDED`。把网页版切到后台，等五六分钟再回来看这一列——如果从 `HIDDEN` 走到了 `FROZEN`，说明白名单没生效或者域名填错了。想看极端情况，直接点该行的 `Urgent Discard`，能手动复现一次"丢弃"。

**第二步，用控制台打点，量出节流有多狠。** 在网页版页面按 `F12` 打开开发者工具，切到 Console，粘一段计时代码：

```js
let n = 0;
setInterval(() => console.log(++n, new Date().toLocaleTimeString()), 30000);
```

然后切去别的标签待 6 分钟回来数行数。正常接近 12 行；只剩 6 行左右说明被节流到 1 分钟一次；中间整段空白、回来才连着蹦出好几行，那就是冻结过。这段代码不写任何数据，只是让页面自己报时。

**第三步，用真实消息验一次往返。** 拿手机端或另一台设备，往「收藏夹」（Saved Messages）或一个只有自己的群发三条带时间戳的消息，然后把 Chrome 窗口最小化、十分钟不碰鼠标键盘。回来检查三件事：桌面右下角有没有弹通知、切回标签时消息是不是已经在那儿、页面有没有闪一下重新加载。

| 你观察到的 | 说明什么 | 接下来做什么 |
| --- | --- | --- |
| 通知弹了，消息也已就位 | 白名单生效，页面没被冻结 | 保持现状，别再加扩展 |
| 消息在，但一条通知没弹 | 页面活着，卡在通知权限或系统层 | 查站点通知权限与系统通知开关 |
| 切回后成批补上、无重载 | 仍在冻结，白名单域名可能填错 | 回 `chrome://settings/performance` 核对域名 |
| 切回白屏重载、草稿丢失 | 已被丢弃，内存压力大 | 固定标签 + 独立窗口 + 降档内存节省强度 |

## 四、一个跨时区值班群的实际教训

我认识的一个小团队，三个人轮班盯一个海外客户群。他们长期把网页版挂在同一窗口的第三个标签上，问题只出在夜间：值班的人切去看监控面板，二十分钟后回来，群里客户已经连发四条"在吗"。

当时他们判断是"网络半夜不稳"。后来查 `chrome://discards`，那个标签的状态一直是 `FROZEN`——页面在切走后第五分钟就停了，夜里没有任何代码在跑。改成固定标签、单独窗口、加进白名单后跑了一周，消息到达延迟从十几分钟降到几秒。

由此衍生的小习惯：**草稿先落在别处**。冻结和丢弃都可能让输入框里的半句话消失，我都在记事本里写好再粘进去，这个动作比任何设置都可靠。

## 五、这几种症状，别往休眠上算

后台延迟和另外几类故障长得很像，判断错了白折腾一轮。

- **一直显示"正在连接"、转圈不停**：页面是活的，是长连接建不起来，通常出在代理或中间网络设备上，跟休眠无关。
- **只有图片、视频加载不出来，文字正常**：多半是拦截类扩展把媒体请求掐了。
- **页面明明在前台，通知照样不弹**：回到权限与系统通知那两级查，休眠这一层可以排除。
- **每次切回来都要求重新登录**：那是会话与 Cookie 的事，[Cookie 与登录状态说明](https://tlgroc-web.com) 里讲得比较透。

## 六、把这五处一次配好，往后就不用靠刷新救火

这套东西的价值在于把网页版从"随时可能被系统回收的后台页"变成"一直在线的窗口"。五处配完大概八分钟。

验证也别省：`chrome://discards` 看状态、控制台数行数、真实消息走一遍往返，三个动作不到十分钟。

真要长期挂着一个聊天窗口干活，我更推荐把网页版拖成窄窗口贴在屏幕边上，占的资源更少，也不容易被当成可回收对象。
